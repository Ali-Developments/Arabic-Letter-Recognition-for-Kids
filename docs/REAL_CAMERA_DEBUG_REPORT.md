# Real Camera Debug & Ruled Paper Robustness Report

## 1. Executive Summary

During live camera evaluation and mobile capture testing of the Arabic handwritten letter recognition system, several inconsistent behaviors were identified:
- Uploaded image files often succeeded (particularly for wide basin letters like ب and ث).
- Live camera captures showed erratic recognition and frequent false rejections.
- Notebook ruled lines, page margins, or stray strokes caused complete prediction failure or false multi-character rejection.
- Clean white-paper samples exhibited inconsistent letter framing.

An end-to-end investigation across both the frontend browser capture client and the backend computer vision pipeline identified two distinct root causes:
1. **Frontend Root Cause:** Viewport-to-sensor aspect ratio distortion in the HTML5 video capture logic.
2. **Backend Root Cause:** Connected-component envelope hijacking and stroke destruction by notebook ruled lines and page border margins.

Both defects have been addressed, verified, and benchmarked without retraining or altering the trained model weights.

## 2. Complete Live Camera Path Trace

```text
1. MediaDevices.getUserMedia({ video: { facingMode: "environment", width: 1280, height: 720 } })
   ↓
2. <video id="video-feed"> displays stream with CSS { object-fit: cover; aspect-ratio: 4/3; }
   ↓
3. Child positions handwritten letter inside on-screen <div class="guide-frame"> (200x200 px)
   ↓
4. captureFrame() triggers:
   - Queries getBoundingClientRect() for both video display and guide-frame overlay
   - Maps on-screen guide coordinates into native video sensor buffer coordinates
   - Adds 15% safety padding to prevent stroke clipping
   - Draws square crop into <canvas id="capture-canvas">
   ↓
5. canvas.toBlob(blob, "image/jpeg", 0.95)
   ↓
6. POST /api/v1/recognize-letter via FormData multipart file upload
   ↓
7. Backend FastAPI Handler:
   - Validates MIME type (image/*)
   - Generates unique request trace ID (e.g., req_1776012921_a4b9c1d2)
   - Decodes bytes into BGR NumPy array via cv2.imdecode
   ↓
8. Computer Vision Preprocessing:
   - Grayscale conversion & lighting check
   - Bilateral edge-preserving filtering
   - Adaptive Gaussian thresholding (21x21, C=10)
   - Ruled-line and border-margin suppression (morphological + component level)
   - Connected-component analysis & spatial envelope Arabic dot preservation
   - Proportional aspect-ratio centering onto 32x32 canvas (margin=8)
   ↓
9. PyTorch ArabicCNN Inference & Dual-Threshold Confidence Management
   ↓
10. JSON Response returned with prediction, confidence, top candidates, and request_id
    ↓
11. Diagnostic Image Export: Saves all intermediate processing stages to debug/real_camera/<request_id>/
```

## 4. Root Causes & Technical Solutions

### A. Frontend Root Cause: Crop Coordinate Misalignment
- **Issue:** The visual guide frame on the screen was a centered 200x200 CSS element inside an aspect-ratio-constrained container, while `captureFrame()` assumed a naive mathematical center crop of the raw sensor video. On wide mobile screens or 16:9 camera sensors, letters drawn near the visual frame were cropped off-center, cutting off character tails or top/bottom dots.
- **Fix:** Implemented `captureFrame()` projection that calculates container aspect ratio vs. sensor aspect ratio, determines letter bounds in video buffer space, and applies a 15% safety margin.

### B. Backend Root Cause: Ruled Notebook Paper & Margin Lines
- **Issue:** Children frequently practice writing on lined or ruled notebook paper. A single horizontal line spanning across the page:
  1. Often had a larger area than the handwritten letter, becoming the `max_label` body and treating the actual letter as an out-of-envelope noise component.
  2. Or triggered the multiple-letter guard (`multiple_letters`), rejecting the image immediately.
- **Fix:**
  - **Phase 1 (Morphological Long Line Suppression):** Used a horizontal structural element (`cv2.MORPH_OPEN` with width $\ge 0.55 \times W$) to detect and subtract thin ruled lines spanning across the page, while protecting Arabic letter basins (which are curved and thicker).
  - **Phase 2 (Edge-Touching Border Line Removal):** Detected long vertical lines touching image boundaries (margin lines, camera framing edges) without affecting centered vertical strokes like Alef (أ).
  - **Phase 3 (Component-Level Geometry Filter):** Filtered residual thin line components with aspect ratio $W/H \ge 8.0$ or $H \le 6\text{ px}$.

### C. Arabic Dot & Diacritic Preservation
- To ensure dots are never pruned alongside noise or lines:
  - Small secondary components ($\text{area} \ge 2\text{ px}$) within the expanded envelope ($0.75 \times W$ horizontal, $1.5 \times H$ vertical) are strictly retained.
  - Dot preservation benchmark maintained **100%** survival across faint and weak dot test cases.

## 5. Diagnostic Request Tracing (`debug/real_camera/`)

Every recognition request now receives a unique trace ID (`req_<timestamp>_<uuid>`), returned in the API response:
```json
{
  "success": true,
  "request_id": "req_1776012952_3f8e12a4",
  "prediction": { "letter": "ب", "confidence": 0.9995, "accepted": true }
}
```

The backend automatically persists step-by-step diagnostic visualizations in `debug/real_camera/<request_id>/`:
1. `original_received.jpg` — Raw incoming image bytes as received by the API.
2. `grayscale.png` — Grayscale luminosity map.
3. `threshold.png` — Output of Adaptive Gaussian Thresholding.
4. `cleaned.png` — Binary mask after ruled line suppression and border removal.
5. `components.png` — Bounding boxes of all preserved character components and dots.
6. `final_32x32.png` — Uniformly scaled, aspect-ratio-centered model input.
7. `final_28x28.png` — Resized 28x28 diagnostic view.

## 7. Remaining Limitations & Edge Cases

1. **Strokes Directly Crossing Multiple Heavy Grid Lines (Graph Paper):**
   - Fine, thin notebook lines (1–3 px) are suppressed cleanly.
   - Extremely dark, heavy graph paper grids (crosshatch grids every 5 mm) can break up thin stroke connectivity.
2. **Rotational Skew $> 25^\circ$:**
   - Preprocessing centers and scales characters regardless of rotation, but the baseline CNN model was trained primarily on upright handwriting.
3. **Real Mobile Device Field Validation:**
   - The pipeline is development complete and camera-debugged. However, formal validation across a large physical corpus of mobile phone captures remains the scheduled next stage.

## 8. Selected Interaction Paradigm: Live Camera Preview + Explicit Capture & Recognize

The project evaluated continuous background auto-recognition (Step 4.6), but by deliberate product decision, continuous automated inference was removed in favor of intentional capture:
- **Rationale**: Continuous background inference creates unnecessary device heating, network traffic, motion-blur false triggers, and UI distraction for young learners.
- **Final Supported Interaction**:
  1. Live video preview enables the child to comfortably align their handwriting inside the on-screen guide frame.
  2. The child taps **"⚡ التقاط وتعرّف فوري (Capture & Recognize)"**.
  3. A single high-resolution square frame is cropped, preprocessed, and dispatched to `/api/v1/recognize-letter`.
  4. The model returns the predicted letter, confidence, and candidate ranking, driving an immediate game victory or gentle retry reaction.
  5. Fallback image upload remains fully functional for asynchronous testing.
